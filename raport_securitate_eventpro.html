01

Prezentare generală

Ce urmărește evaluarea și cum trebuie citite rezultatele.

Obiectiv

Documentul oferă o bază de lucru pentru evaluarea securității site-ului EventPro (organizare evenimente). Scenariile vizează clase comune de probleme: injectarea de date în formulare, expunerea informațiilor, validarea inputurilor, configurarea HTTP și eventualele fluxuri de autentificare sau administrare.

Într-un site de organizare evenimente pot exista funcții precum paginile de servicii, portofoliu, pachete, testimoniale, formularul de solicitare ofertă și eventualele zone de administrare. Nu presupune că toate aceste funcții sau rute există; verifică documentația aplicației și comportamentul autorizat al acesteia.

🔎

Identificare

Confirmă paginile, metodele HTTP, endpoint-urile și tipurile de date acceptate.

🧪

Verificare

Compară comportamentul observat cu criterii explicite și reproductibile.

🧰

Remediere

Prioritizează riscurile, aplică măsuri corective și repetă testele.

Regulă de interpretare

Un test trecut înseamnă doar că verificarea specifică a trecut. Nu reprezintă o certificare de securitate și nu exclude alte vulnerabilități.

02

Domeniu, autorizare și pregătire

Stabilește limitele înainte de a trimite cereri.

Înainte de testare

  • Confirmă în scris că ai permisiunea de a testa domeniul și API-urile aferente.
  • Preferă un mediu de staging sau o copie locală a aplicației.
  • Folosește conturi de test și date fictive; nu modifica datele reale ale clienților sau solicitările de ofertă.
  • Stabilește o limită de trafic și o perioadă de testare.
  • Nu încerca să accesezi secrete, conturi sau fișiere reale care nu îți aparțin.
  • Oprește testul dacă observi degradarea serviciului sau acces la date neașteptate.

În domeniu

Rutele și serviciile aprobate, testele neintruzive, verificarea răspunsurilor și validarea controalelor în conturi de test.

În afara domeniului fără aprobare separată

Atacuri de volum, scanări agresive, exploatarea infrastructurii terțe, extragerea datelor și testarea conturilor altor persoane.

Autentificare și protecția conturilor

Scenarii de verificare a formularului de contact și a eventualelor fluxuri de autentificare.

POST

4.1 Validare input — Formular Contact (SQL/NoSQL)

Validare input
{{baseUrl}}/contact.html · formular de confirmat · rută de confirmat

Scop: verifică dacă serverul (dacă există) tratează câmpurile formularului (nume, email, telefon, mesaj) ca date, fără să le interpreteze ca fragmente de interogare.

Ce verifică scriptul inițial

  • Răspunsul nu este o eroare internă HTTP 500.
  • Corpul nu conține mesaje uzuale de eroare SQL.
  • Autentificarea respinge datele de test.
  • Timpul de răspuns rămâne într-un prag orientativ.
Limitare

Un prag de 5 secunde nu este o probă de securitate, iar un status specific nu dovedește singur absența injecției. Pentru confirmare, verifică folosirea interogărilor parametrizate și logurile aplicației în mediul de test.

Remediere recomandată

Folosește interogări parametrizate sau un ORM utilizat în siguranță, validare de tip pe server și mesaje de eroare generice. Nu concatena inputul utilizatorului în interogări.

Exemplu de verificări Postman
pm.test("Răspunsul nu este o eroare internă", function () {
  pm.expect(pm.response.code).to.not.equal(500);
});

pm.test("Răspunsul nu expune mesaje SQL", function () {
  const body = pm.response.text().toLowerCase();
  const markers = ["sqlstate", "syntax error", "mysql_fetch", "pg_query"];
  markers.forEach(function (marker) {
    pm.expect(body).to.not.include(marker);
  });
});

4.2 XSS — Formular Solicitare Ofertă

Input și output
{{baseUrl}}/contact.html · formular de confirmat · rută de confirmat

Scop: verifică tratarea sigură a câmpurilor (nume, mesaj, tip eveniment) care conțin markup HTML. XSS apare când datele controlate de utilizator sunt interpretate ca script în browser.

Ce verifică

  • Serverul nu se prăbușește la date neașteptate.
  • Răspunsul nu reflectă anumite fragmente periculoase nefiltrate.
  • Codul HTTP este compatibil cu comportamentul documentat al înregistrării.
Limitare

Căutarea literală a unui singur șir nu acoperă toate formele de XSS. De asemenea, HTML-ul poate fi stocat și redat mai târziu în altă pagină. Testează randarea în interfață folosind un cont și date de test.

Remediere recomandată

Aplică escaping contextual la afișare, folosește API-uri DOM sigure, validează câmpurile conform formatului și configurează o Content Security Policy ca strat suplimentar, nu ca înlocuitor pentru cod sigur.

Exemplu de verificări Postman
pm.test("Răspunsul nu este HTTP 500", function () {
  pm.expect(pm.response.code).to.not.equal(500);
});

pm.test("Răspunsul nu reflectă markerul de test", function () {
  const body = pm.response.text().toLowerCase();
  pm.expect(body).to.not.include("onerror=alert");
});

4.3 Rate Limit — Formular Contact

Protecție cont
{{baseUrl}}/contact.html · formular de confirmat · rută de confirmat

Scop: evaluează dacă trimiterea repetată a formularului de contact este limitată și dacă răspunsurile nu divulgă informații inutile.

Ce verifică

  • Autentificarea eșuată returnează un răspuns documentat.
  • După pragul configurat, serverul aplică o limită, o întârziere sau o altă măsură de protecție.
  • Mesajele nu dezvăluie detalii sensibile despre starea contului.
Important

Nu rula bucle agresive împotriva serviciului public. Folosește staging, un cont fictiv și un număr mic de cereri aprobat. Testul nu trebuie să blocheze utilizatori reali.

Remediere recomandată

Aplică limitare pe mai multe dimensiuni, cum ar fi IP și cont, monitorizare, backoff și protecție contra automatizării. Evită să te bazezi exclusiv pe IP.

Exemplu de verificare a unui răspuns de autentificare
pm.test("Autentificarea eșuată are un status acceptat", function () {
  pm.expect([400, 401, 403, 429]).to.include(pm.response.code);
});

pm.test("Răspunsul nu expune stack trace", function () {
  const body = pm.response.text().toLowerCase();
  pm.expect(body).to.not.include("node_modules");
  pm.expect(body).to.not.include(" at object.");
});

4.4 Enumerare / Diferențe de răspuns — Formular

Confidențialitate
{{baseUrl}}/contact.html · flux de confirmat · rută de confirmat

Scop: verifică dacă răspunsurile formularului (sau orice flux de confirmare) permit enumerarea prin diferențe de mesaj sau status.

Ce verifică

  • Mesajul pentru o adresă necunoscută este generic.
  • Răspunsul nu conține mesaje explicite de tip „cont inexistent”.
  • Timpii de răspuns sunt suficient de consecvenți pentru a nu divulga informații evidente.

Metodă: compară o adresă de test existentă și una fictivă, folosind numai conturi pe care le controlezi. Compară codul, forma mesajului și timpul în mai multe probe controlate.

Remediere recomandată

Returnează un mesaj generic, limitează cererile și nu dezvălui dacă adresa există. Tokenurile de resetare trebuie să fie aleatoare, de unică folosință și să expire.

Exemplu de verificare Postman
pm.test("Solicitarea de resetare nu expune o eroare internă", function () {
  pm.expect(pm.response.code).to.not.equal(500);
});

pm.test("Mesajul nu divulgă existența contului", function () {
  const body = pm.response.text().toLowerCase();
  pm.expect(body).to.not.include("not registered");
  pm.expect(body).to.not.include("cont inexistent");
  pm.expect(body).to.not.include("no account");
});

5.1 Security Headers — Homepage

Configurare
{{baseUrl}}/ · URL de bază confirmat separat

Scop: verifică prezența și valoarea unor antete care reduc riscurile din browser. Antetele necesare depind de arhitectura și funcțiile aplicației.

AntetRolCe verifici
Content-Security-PolicyLimitează sursele de conținut încărcat.Politică potrivită aplicației; evită surse excesiv de largi.

Stabilește un baseline pentru aplicație și marchează lipsa unei măsuri drept constatare numai după evaluarea contextului. Un test care doar afișează warning și apoi trece nu trebuie prezentat ca verificare reușită.

Remediere recomandată

Configurează antetele la nivelul aplicației sau al platformei de hosting, verifică paginile HTML și răspunsurile API separat și repetă testele după deploy.

Exemplu Postman: verificarea unui antet
pm.test("X-Content-Type-Options este configurat", function () {
  const value = pm.response.headers.get("X-Content-Type-Options");
  pm.expect(value, "Antet lipsă").to.exist;
  pm.expect(value.toLowerCase()).to.include("nosniff");
});

5.2 CORS Policy Check

Cross-origin
{{baseUrl}}/contact.html · formular de confirmat · rută de confirmat

Scop: verifică ce origini web sunt autorizate să citească răspunsurile API prin browser. CORS este o politică aplicată de browser, nu un mecanism de autentificare.

Ce verifică

  • Originea de test neaprobată nu este reflectată automat în Access-Control-Allow-Origin.
  • Politica pentru credențiale este compatibilă cu origini explicite.
  • Cererile preflight permit doar metode și antete necesare.
Interpretare corectă

Absența antetului CORS nu dovedește că serverul blochează toate cererile cross-origin; cererile pot ajunge la server chiar dacă browserul nu permite citirea răspunsului. Wildcard-ul nu este automat vulnerabil dacă API-ul nu expune date protejate și nu folosește credențiale.

Remediere recomandată

Folosește o listă exactă de origini aprobate, metode și antete strict necesare. Nu reflecta orbește antetul Origin și nu considera CORS substitut pentru autorizarea pe server.

Exemplu Postman: verificare de bază
pm.test("Originea de test nu este aprobată automat", function () {
  const origin = pm.response.headers.get("Access-Control-Allow-Origin") || "";
  pm.expect(origin).to.not.include("evil-attacker.com");
});

6.1 Acces neautorizat — Zone private / Admin

Autorizare
{{baseUrl}}/ · resurse private de confirmat · rută de confirmat

Scop: confirmă că resursele private (dacă există) nu pot fi citite fără autentificare.

Pași

  • Confirmă ruta cu documentația sau aplicația.
  • Trimite o cerere fără antetul Authorization, într-un mediu aprobat.
  • Compară răspunsul cu cererea unui utilizator de test autentificat.
  • Verifică dacă datele private sunt returnate numai utilizatorului autorizat.

Rezultat așteptat: refuzul accesului sau un răspuns public documentat. Un 404 poate însemna că ruta nu există (site static), nu neapărat că autorizarea este bună.

Remediere recomandată

Aplică verificarea autentificării și autorizării pe server la fiecare cerere. Nu te baza pe ascunderea butoanelor din interfață.

Exemplu Postman
pm.test("Ruta privată nu oferă acces anonim", function () {
  pm.expect([401, 403]).to.include(pm.response.code);
});

6.2 Token / Sesiune invalidă (dacă există)

Token
{{baseUrl}}/ · resurse private de confirmat · rută de confirmat

Scop: verifică respingerea tokenurilor care nu pot fi validate sau care nu au permisiunile necesare.

Ce trebuie acoperit

  • Token absent.
  • Token malformat sau cu semnătură invalidă.
  • Token expirat.
  • Token valid, dar emis pentru un rol insuficient.

Un token valid criptografic nu înseamnă automat că utilizatorul are dreptul să acceseze orice resursă. Autorizarea trebuie verificată separat.

Remediere recomandată

Validează semnătura, algoritmii acceptați, expirarea și claims relevante. Folosește o bibliotecă matură și nu dezvălui detalii despre chei sau implementarea internă în erori.

Exemplu Postman
pm.test("Tokenul invalid este respins", function () {
  pm.expect([401, 403]).to.include(pm.response.code);
});

6.3 Path Traversal — Resurse / Imagini

Acces la resurse
{{baseUrl}}/portfolio.html · resurse de confirmat · rută și parametru de confirmat

Scop: evaluează dacă un parametru folosit pentru identificarea unei resurse este validat și nu poate fi reinterpretat ca o cale de fișier.

Limită de aplicabilitate

Dacă parametrul id este doar un identificator de produs și nu este folosit pentru citirea fișierelor, scenariul nu este un test valid de Path Traversal. Confirmă mai întâi implementarea și folosește fișiere canar neconfidențiale într-un mediu controlat.

Remediere recomandată

Folosește identificatori allowlist, rezolvă fișierele într-un director fix și verifică calea finală înainte de acces. Evită să expui fișiere de configurare sau directoare interne.

Exemplu de verificări generice
pm.test("Răspunsul nu este o eroare internă", function () {
  pm.expect(pm.response.code).to.not.equal(500);
});

pm.test("Răspunsul nu conține marcatori de fișiere sensibile", function () {
  const body = pm.response.text();
  pm.expect(body).to.not.include("root:x:0:0");

7.1 Injecție NoSQL / Tipuri greșite — Contact

Validare JSON
{{baseUrl}}/contact.html · formular de confirmat · rută de confirmat

Scop: verifică dacă API-ul respinge obiecte acolo unde schema cere șiruri de caractere și dacă valorile clientului pot schimba logica interogărilor.

Ce verifică

  • Tipurile de date sunt validate strict pe server.
  • Erorile bazei de date nu sunt expuse în răspuns.
  • Un răspuns de succes nu este confundat cu o autentificare efectivă.

Remediere recomandată

Definește o schemă pentru fiecare request, respinge tipurile nepermise, construiește interogări prin API-uri sigure și nu accepta operatori de interogare direct din input.

Exemplu Postman
pm.test("Serverul nu expune erori interne", function () {
  const body = pm.response.text().toLowerCase();
  pm.expect(body).to.not.include("mongoose");
  pm.expect(body).to.not.include("casterror");
});

7.2 Mass Assignment — Câmpuri sensibile în formular

Escaladare privilegii
{{baseUrl}}/contact.html · formular de confirmat · rută de confirmat

Scop: verifică dacă un utilizator poate seta câmpuri sensibile (rol, isAdmin, status) prin formular sau request, dacă există backend de înregistrare/admin.

Ce verifică

  • Serverul acceptă doar câmpurile permise.
  • Rolul este atribuit server-side și nu provine din inputul clientului.
  • Starea efectivă a contului este verificată, nu doar câmpurile incluse în răspuns.
De ce scriptul simplu poate rata problema

Dacă răspunsul nu include role sau isAdmin, testul poate trece fără să verifice privilegiile reale. Înregistrează numai conturi de test și verifică starea cu o rută administrativă autorizată sau în baza de date de test.

Remediere recomandată

Folosește allowlist pentru câmpurile de intrare, DTO-uri/scheme explicite și atribuirea rolului pe server. Nu copia automat întregul obiect JSON în modelul utilizatorului.

Exemplu de verificare pentru câmpuri din răspuns
pm.test("Răspunsul nu acordă explicit rol admin", function () {
  if (pm.response.code === 200 || pm.response.code === 201) {
    const body = pm.response.json();
    const role = body.role || (body.user && body.user.role);
    if (role !== undefined) {
      pm.expect(role).to.not.equal("admin");
    }
  }
});

Principii generale de validare

Validare pe server

Validarea din browser îmbunătățește experiența, dar nu poate înlocui verificarea server-side.

Tipuri și limite

Verifică tipul, lungimea, formatul, intervalul numeric și câmpurile permise.

Erori sigure

Returnează mesaje utile utilizatorului fără stack trace, secrete sau interogări interne.

Teste negative

Include valori lipsă, valori excesive și tipuri neașteptate, fără a afecta date reale.

Recomandări de remediere

Acțiuni concrete pentru dezvoltare și operare.

Prioritatea 1 — Controale esențiale

  • Verifică autentificarea și autorizarea server-side pentru fiecare resursă privată.
  • Asigură izolarea solicitărilor între utilizatori și aplică verificări la nivel de obiect.
  • Folosește interogări parametrizate și validare strictă a schemelor.
  • Asigură-te că rolurile privilegiate nu pot fi setate de client în fluxul de înregistrare.
  • Calculează prețurile, reducerile și totalurile pe server.

Prioritatea 2 — Hardening și observabilitate

  • Definește un baseline de antete HTTP și verifică-l automat în pipeline.
  • Configurează CORS cu o listă explicită de origini aprobate.
  • Limitează încercările de autentificare și operațiile costisitoare.
  • Redactează date sensibile din loguri și erori.
  • Actualizează dependențele și verifică vulnerabilitățile acestora prin procese de dezvoltare autorizate.

Prioritatea 3 — Proces continuu

  • Adaugă teste de regresie pentru fiecare constatare remediată.
  • Revizuiește periodic inventarul API și permisiunile rolurilor.
  • Documentează schimbările de arhitectură și impactul asupra securității.
  • Separă mediile de dezvoltare, test și producție.
  • Planifică o evaluare independentă atunci când riscul și contextul o justifică.

False positiveUn rezultat pare să indice o problemă, dar investigația arată că nu este o vulnerabilitate.
False negativeTestul nu detectează o problemă care există în realitate.

PASS nu înseamnă „aplicație sigură”

Înseamnă doar că verificarea formulată a trecut. Testele trebuie să fie suficient de precise pentru a evalua comportamentul real.

FAIL nu înseamnă automat exploatare

Un rezultat eșuat poate indica un defect de test, un endpoint inexistent sau o problemă de configurare. Confirmă impactul înainte de raportare.
